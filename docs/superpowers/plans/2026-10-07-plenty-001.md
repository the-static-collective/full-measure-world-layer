# PLENTY-001 Scarcity Inverter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a pure Full Measure-local evaluator that reports how many presently viable, dependency-independent paths reach a declared need without upgrading proposal, stale evidence, access, or model output into capacity.

**Architecture:** Add a focused `src/lib/plentySpecimen/` domain with immutable input/output types, one deterministic evaluator, and pinned hostile fixtures. The evaluator validates truth-state first, derives structural completeness and present viability second, then computes a deterministic maximum set of pairwise dependency-disjoint viable paths; it never mutates Garden measures or calls donor systems.

**Tech Stack:** TypeScript 5.8, Node `node:test` / `node:assert/strict`, existing repository `npm run check` gate, no new production dependencies.

**Spec:** `docs/superpowers/specs/2026-10-07-plenty-001-design.md`

## Global Constraints

- Full Measure-local and dependency-free.
- `PLENTY MAY REPORT POSSIBILITY. IT MAY NOT MANUFACTURE CAPACITY.`
- `PARTICULAR != CAPABILITY != AVAILABILITY != ACCESS != AUTHORITY`.
- Unknown state never upgrades itself to true or false.
- `model-output`, `plenty-receipt`, and `self-report` provenance cannot enter as witnessed evidence.
- Stale or unknown-currentness claims cannot establish present viability.
- Duplicate surface representations and shared dependency aliases cannot inflate independent path count.
- Independent path count is the size of the deterministic maximum set of presently viable paths whose normalized critical dependency sets are pairwise disjoint.
- Tie-break equal maximum independent sets lexicographically by `pathRef`.
- Evaluation never mutates input particulars, claims, candidate paths, or source refs.
- PLENTY receipts have no authority beyond their inputs and computation.
- No UI, route, persistence, network access, GHoT, Rack, reLATTE, SupaBardo, TranchNode, donor mutation, purchase optimization, or Garden measure mutation in 001.
- Broad verification gate: `npm run check`.

## File Structure

- `src/lib/plentySpecimen/types.ts` — exported domain types only: need, particulars, capability claims, constraints/results, candidate paths, path receipts, evaluator input, receipt/disposition.
- `src/lib/plentySpecimen/index.ts` — `evaluatePlenty()`, validation, structural/viability classification, dependency-set normalization, deterministic independence calculation, and `PlentySpecimenError`.
- `src/lib/plentySpecimen/fixtures.ts` — the canonical power-cut specimen and small deterministic fixture builders reused by tests; no runtime discovery.
- `tests/plenty-specimen.test.ts` — all positive, boundary, malformed-input, and BAT hostile proofs.
- No existing production file is modified unless broad verification exposes a required import/build issue.

## Review Focus

The five easy-to-miss failure modes are pinned into the owning tasks below:

1. **A capability listed twice inside one path** must not double-count or manufacture a second dependency-free route.
2. **A hard need constraint omitted from a candidate's results** must remain unresolved rather than silently treated as satisfied.
3. **Two maximum independent sets with equal size** must select the lexicographically smallest `pathRef` set deterministically.
4. **A validation failure after earlier valid entries** must be atomic: inputs remain untouched and no partial receipt escapes.
5. **An empty critical-dependency set** may represent a genuinely dependency-free path, but multiple duplicate paths with the same capability chain still must not inflate independent count.

export interface PlentyNeed {

export interface PlentyParticular {

export interface PlentyCapabilityClaim {
  capabilityRef: string;
  particularRef: string;
  capability: string;
  evidenceClass: PlentyEvidenceClass;
  provenanceKind: PlentyProvenanceKind;
  currentness: PlentyCurrentness;
  availability: PlentyTruthState;
  access: PlentyAccessState;
  authority: PlentyAuthorityState;
  dependencyRefs: string[];
  requiresCapabilityRefs: string[];
  sourceRefs: string[];
  reproductiveEvidenceRefs?: string[];
}

export interface PlentyCandidatePath {
  pathRef: string;
  needRef: string;
  capabilityRefs: string[];
  dependencyRefs: string[];

export interface PlentyEvaluationInput {
  need: PlentyNeed;
  particulars: readonly PlentyParticular[];
  capabilities: readonly PlentyCapabilityClaim[];

export interface PlentyPathReceipt {
  pathRef: string;
  structuralState: "complete" | "incomplete";
  viabilityState: "viable" | "blocked" | "unresolved";
  dependencyRefs: string[];
  blockingRefs: string[];
  unresolvedRefs: string[];
}

export interface PlentyReceipt {
  needRef: string;
  candidatePathCount: number;
  structurallyCompletePathCount: number;
  viablePathCount: number;
  independentPathCount: number;
  independentPathRefs: string[];
  blockingDependencyRefs: string[];
  fragileDependencyRefs: string[];
  unusedCapabilityRefs: string[];
  unresolvedClaimRefs: string[];
  pathReceipts: PlentyPathReceipt[];
  disposition:
    | "NO_KNOWN_PATH"
    | "POSSIBILITIES_ONLY"
    | "VIABLE_BUT_FRAGILE"
    | "MULTIPATH"
    | "RESILIENT_MULTIPATH";
}

export class PlentySpecimenError extends Error {
  readonly code: string;
}

export function evaluatePlenty(input: PlentyEvaluationInput): PlentyReceipt;

### Task 3: Compute dependency independence and resist path-count inflation

**Files:**
- Modify: `src/lib/plentySpecimen/index.ts`
- Modify: `tests/plenty-specimen.test.ts`

**Interfaces:**
- Consumes: viable path receipts and normalized dependency refs from candidate paths plus capability claims.
- Produces: `independentPathCount`, `independentPathRefs`, `fragileDependencyRefs`, `blockingDependencyRefs`, and final multi-path dispositions.

Dependency set for a path is the deduplicated union of:
1. `candidatePath.dependencyRefs`; and
2. every participating capability's `dependencyRefs`.

- [ ] **Step 1: Write RED inventory-inflation and alias tests**

Assert:
- 1,000 candidate copies of the same path identity are rejected as contradictory duplicate identity or deterministically deduplicated without count inflation; choose one behavior and pin it consistently as `PLENTY_PATH_CONFLICT` for contradictory duplicates and one retained path for byte-equivalent duplicates;
- multiple surface labels sharing `dependency:power:grid-a` remain one dependency family;
- duplicate capability refs inside one path do not create independence.

- [ ] **Step 2: Write RED shared choke-point and correlated-failure tests**

Assert:
- ten viable paths that all require `dependency:car:1` produce `viablePathCount === 10` and `independentPathCount === 1`;
- three providers sharing one upstream provider remain correlated;
- forty routes requiring the same person remain one fragile family.

- [ ] **Step 3: Write RED true multipath tests**

Create three viable paths:
- A depends on `power:grid`;
- B depends on `power:solar`;
- C depends on `power:grid` + `person:sam`.

Assert maximum pairwise-disjoint set is A+B or B+C, and lexicographic `pathRef` tie-breaking chooses the smaller sorted ref set. Assert `independentPathCount === 2`.

Also assert two genuinely dependency-free, non-duplicate capability chains may both count as independent.

- [ ] **Step 4: Write RED adversarial-cardinality and path-destruction tests**

Assert:
- 10,000 syntactic candidate variants around one dependency family do not raise independent count above one;
- removing or marking one dependency-bearing capability unavailable recomputes only affected paths and leaves unrelated viable paths intact.

- [ ] **Step 5: Implement normalized dependency sets and deterministic maximum independence**

Add:

```ts
function derivePathDependencyRefs(...): string[];
function chooseIndependentPathRefs(
  viablePaths: readonly PlentyPathReceipt[]
): string[];
```

Use exact normalized refs supplied by input. Find the maximum pairwise-disjoint set deterministically; 001 may use bounded exhaustive/backtracking search because this is a proof specimen, but it must prune deterministically and preserve lexicographic tie-breaking. Do not introduce a graph library.

- [ ] **Step 6: Implement fragility and final dispositions**

Pin:
- viable path(s) with independent count 1 => `VIABLE_BUT_FRAGILE`;
- independent count >1 with at least one dependency shared by two or more viable paths => `MULTIPATH`;
- independent count >1 and no declared dependency is shared across viable paths => `RESILIENT_MULTIPATH`.

`fragileDependencyRefs` are normalized dependency refs used by at least two viable paths. `blockingDependencyRefs` are dependency refs appearing on blocked paths because a required capability tied to that dependency is unavailable/inaccessible/unauthorized/stale.
